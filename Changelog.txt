- v1.4.0
### Additions
- Added an automatic game-version check before a Skyrim Special Edition collection installs, and a one-click fix. Bethesda changes SkyrimSE.exe whenever Creation Club content changes and Steam always serves the newest build (1.7.104), but SKSE64 — which nearly every collection needs — supports only an older one (1.6.1170); collections like Gate To Sovngarde list the SRS runtime-swap mod to get there. Its version.dll hook never worked under Wine and its patched base files were undone by the next deploy (Mosaic keeps a Data_Core backup of vanilla files), so Mosaic now applies the mod's own hash-verified HDiffPatch patches itself and never installs that mod. Before any profile is created or anything is downloaded, a collection that lists it is checked against the installed game; if the game isn't at the runtime it needs, a dialog offers "Fix and continue": Mosaic fetches the patch archive (the download cache, else a Premium download, checked against the collection's md5), restores the game first if mods are deployed, backs up the nine files it changes (SkyrimSE.exe, SkyrimSELauncher.exe, the five base .esm files and two base .bsa archives), patches each into a temporary file, checks it against the expected SHA-256, swaps them in all at once (rolling everything back if any step fails), and re-checks. A game that already is at the right version, or a collection that doesn't need it, sees no dialog. It refuses to patch files that are not the original build (it names them and points to Steam's "Verify integrity of game files"), and stops while Skyrim is running. Because the files are patched while the game is restored, the next deploy captures the patched files as its vanilla backup, so a deploy no longer undoes the switch. It uses the hpatchz tool: on PATH if you have it, otherwise Mosaic downloads the pinned upstream release (SHA-256 checked) into its own config folder on first use. Also added a "Skyrim Runtime (game version)" wizard (Setup & Installers) that shows the installed version and reverts a Mosaic switch from its hash-checked backup. A Steam update replaces the patched files, and the check simply runs again next time
- Added a disk-space check before any collection install (blocks when the mods clearly can't fit, warns when their downloaded archives on top might not) and a check after a Skyrim collection installs that the profile's SKSE64 (the skse64_x_y_z.dll name says which runtime) matches SkyrimSE.exe — a mismatch used to launch the game and silently do nothing
- Added a report of the mods that did not install: after a collection install, a dialog now names every mod that is not in the profile and why (before, only the log said so, and the toast just counted "N skipped"), and the same list is saved as install_report.json in the profile. Press Install on the collection again and choose Continue to retry them
- Added author notes to Baldur's Gate 3's Load Order Insights and Sort Load Order: Mosaic reads each enabled Nexus mod's page description (public data, no login; about 20 mods per request, cached and re-read after 7 days) and keeps the sentences about load order, incompatibilities and requirements — e.g. "install Better Inventory UI after Better Containers, BCPP and Better Hotbar 2" or "needs to be below MCM". When such a sentence names another mod you have installed, Load Order Insights shows it: as "already followed" when your order agrees, or with "Accept author note" (saved as a "load after" choice) when it doesn't; nothing is applied without a click. Names in prose are matched loosely but carefully ("Better Container", "BCPP", "Better Hotbar 2"; not a trailing "- MCM", Roman numerals or "VFX support"), and "make sure MCM is higher than X" is read the right way round. Sort Load Order shows the selected mod's notes, "Refresh author notes" re-reads the pages, and "Copy as known-rule suggestion" puts a ready entry for the shared known-rules list on the clipboard. Load Order Insights also flags two enabled mods that are the same module — the same .pak file or module ID, e.g. KAVT and the Unique Tav .pak it replaces — since only one of them is used
- Added a built-in list of known Baldur's Gate 3 load-order rules that mod authors state on their pages but no file records — e.g. Better Inventory UI must load after Better Containers, BCPP and Better Hotbar 2 — plus known incompatibilities and the well-known mods pinned to a layer (ImpUI, Mod Configuration Menu, Compatibility Framework…). Sort Load Order follows these rules above its automatic layers, but below dependencies, a collection's order and your own decisions (a rule that clashes with one of those is listed, not forced), and names the rule in the preview. Load Order Insights marks an overlap the rules explain as "Intended (author rule)" and warns when two known-incompatible mods are enabled together. The list ships with Mosaic and is refreshed from Mosaic's GitHub repository at most once a day, so new rules arrive without an update. Load Order Insights also warns when a mod asks for a newer version of a dependency than the one installed
- Replaced Baldur's Gate 3's "Sort Load Order (Dependencies)" wizard with a full built-in "Sort Load Order" (Wizard ▸ Load Order and Config), for anyone who wants a sorted list without an external curated order. Mods are arranged in layers, loading first to last: Frameworks & UI, Libraries & Resources, Gameplay, Story & Companions, Items & Equipment, Visuals & Customisation, Miscellaneous, Patches and Late loaders. The layer comes from a built-in list of well-known mods (ImpUI, Mod Configuration Menu, Community Library, Compatibility Framework…), meta.lsx patch/library markers, the mod's Nexus category, or its mod.io tags for mod.io installs. Inside a layer the current order is kept, and stronger than any layer are a collection's own load order (a collection's mods are never moved), declared dependencies and the user's Load Order Insights decisions; anything that can't be satisfied is listed instead of forced. The preview shows every move and why. Any mod can be moved to another layer or told to "load after" a specific mod, and both choices are saved per profile. Deploy still only fixes dependencies, and after a sort it moves nothing
- Added a "Load Order Insights" wizard for Baldur's Gate 3 (Wizard ▸ Load Order and Config). It reads what each enabled mod's .pak files actually define — stats entries, treasure tables, UI screens, files in shared base-game folders, declared incompatibilities (meta.lsx Conflicts) and variants of the same mod (info.json Group) — and lists every place two or more mods define the same thing, with the mod that currently wins (the one loading later in modsettings.lsx). The dependency sort can't see any of this: on one 455-mod profile it found Combat Extender and Ultimate NPC Stat Overhaul defining the same 174 stats entries, where only 7 mod pairs shipped an identical file. Anything that isn't a real conflict is filtered out: identical definitions, treasure tables marked CanMerge (the game merges those), and patches that declare the mods they override. "Make it win" moves the chosen mod just above the others and saves the decision as a per-profile rule (refused if it would break a declared dependency, and not undone by deploy's dependency sort). "Ignore" hides a finding, and "Keep current order" saves the current winner as the decision without moving anything. It also compares the named templates and styles UI mods ship in their GUI libraries (e.g. Better Inventory UI, Advanced Character Sheet and BCPP all replace the same inventory templates), and in a collection profile it follows the collection's order. A mod named as a patch or compatibility mod that doesn't declare what it patches is suggested as one, and "Accept as patch" settles all of its findings in one click. Deploy logs a single line while decisions are still open. The first scan takes a couple of seconds; later scans reuse a per-profile cache and only re-read changed paks
- Added a "Downgrade Fallout 4" wizard (under Setup & Installers) that downgrades the Anniversary Edition (1.11.240) Steam now serves to Old-Gen (1.10.163), which Old-Gen mod collections and the 0.6.23 script extender need — on one such collection, F4SE loaded only 6 of its 63 plugins on the current version. It applies the community xdelta patch to Fallout4.exe, Fallout4Launcher.exe and steam_api64.dll natively, with no Wine involved (the collection-bundled FO4Down downgrader is a terminal UI that can't run under Proton), backs the originals up first, verifies the patched Fallout4.exe really reads as 1.10.163 before swapping anything in, rolls everything back if any step fails, and can revert to the Anniversary Edition from the same page. It also checks the things that would make a downgrade go wrong — the game running, xdelta3 missing, or Mosaic's mods being deployed (deploy parks Steam's real launcher in Fallout4Launcher.bak, so the wizard offers to Restore first) — and it stays out of Steam's own files beyond those three, so a later Fallout 4 update from Steam replaces them and the wizard can simply be run again. When the game has newer-format archives (every current Steam install does — most of its own archives are v7/v8), the final page now also says to install the Backported Archive2 Support System and Address Library for F4SE Plugins next to F4SE 0.6.23: without them the Old-Gen game cannot read its own data and shows a black screen and exits with no error. Needs xdelta3: bundled in the AppImage, otherwise install the xdelta3 package
### Bug Fixes
- Fixed FOMOD installers that gate an option behind an empty <dependencies operator="Or"> installing nothing. An empty Or is false ("any of nothing"), as in MO2 and Vortex, but Mosaic treated it as satisfied, so a <dependencyType> pattern that was meant to almost never match made every option in its group Not Usable; the collection author's recorded choice was then refused, no flags were set, the later steps stayed hidden and the mod staged no files. Every retry failed the same way. Found on Glowing Mushroom Collision Fixes in Gate To Sovngarde, the one mod of 1,964 that did not install. The failed-mods dialog now also says when pressing Install again cannot help (only download failures are worth retrying) and describes a mod that produced no files in plain words
- Fixed an unexpected error during a collection install being treated as a cancel: it deleted the newly created profile with everything installed so far and, with "clear archives after install" on, the whole download cache. It now keeps both, says what stopped the install, and Install → Continue resumes it
- Fixed a network blip during a collection install opening a browser tab for every mod (each waiting up to 15 minutes): a dropped connection, a timeout or a Nexus server error is now retried after 3, 10 and 30 seconds and never falls back to the browser; a real refusal (an archived file the API won't serve) still does
- Fixed corrupt or truncated downloads being installed unchecked: a freshly downloaded collection archive is now checked against the collection's md5, deleted and downloaded once more on a mismatch, and reported as a failed mod (with the reason) if it is wrong twice
- Fixed a collection mod whose FOMOD ModuleConfig.xml can't be parsed being sent to the BAIN picker; it now installs verbatim, as the log line already claimed
- Fixed Mosaic picking a stale Proton prefix from the default Steam library over the game's own: Steam keeps a game's prefix in the library the game is installed in, and the finder now looks there first. It also no longer overwrites a prefix you configured that is only temporarily missing (a drive that hasn't mounted yet) with whichever one it found
- Fixed deploy warning about missing mod requirements you had already dismissed one by one (the Missing Requirements panel's per-requirement ignore): the Mods-tab flag respected it, deploy didn't. Deploy now also accepts either/or requirements from Mosaic's requirement filter, which gains Unique Tav → KAVT (KAVT is Unique Tav's modern replacement, so a Unique Tav requirement is met by KAVT), and the filter copy bundled with Mosaic now counts even before the online copy is updated
- Fixed Baldur's Gate 3 load-order divider mods (e.g. Astra's Load Order Dividers, used for BG3 Mod Manager's and volo's curated sorting) being written into modsettings.lsx. The game then listed every divider as a "New Mod Detected" in its Mod Verification window — 131 of them on one profile. Paks that contain nothing but a meta.lsx are now left out of the load order, unless another mod declares one as a dependency
- Fixed Baldur's Gate 3 mods being flagged as missing a requirement that a fork of that requirement already provides. Nexus lists requirements by mod page, so Companions Panel and Camp Chest Everywhere was reported as missing "ImpUI (ImprovedUI)" (in the deploy warning and the Mods-tab flag) even with ImpUI P8 Fork installed, which carries the same module UUID the game actually checks. A requirement now also counts as met when an installed .pak provides the UUID that the requirement's name maps to in the installed mods' own meta.lsx files
- Fixed removing a mod leaving the game without a file that another enabled mod also provides, until the next Deploy. Reinstalling a mod from Nexus as a second copy and then removing the old one deleted the old copy's deployed file — correctly, it was the removed mod's — but the new copy had never been deployed, so the game had no copy at all: Baldur's Gate 3 Mod Manager then reported Waterproof Shadowheart as missing from the load order. Removing a mod now links the highest-priority enabled mod's copy of each removed file in its place, the same way the removed file was linked (symlink, hardlink or copy)
- Fixed "Run EXE" — and every other launch path that builds its own Proton command (the Morrowind wizards, BodySlide, Synthesis, DTKit, the Fallout 3 downgrade wizard) — failing instantly with "wine: could not load kernel32.dll, status c0000135" against a game's real Steam prefix. A prefix Steam has launched the game in has its Windows DLLs linked through a path that only exists inside Steam's own runtime container, so a tool started from outside it hit dangling links. The workaround had been added one launch path at a time (wizard tools, the VC++ Redistributable installer, the .NET installer, the registry writer), and every new launch path that built its own Proton command reintroduced the failure; it is now applied inside the Proton command builder itself, so no launch path can miss it
- Fixed script-extender archives that ship their loader as loose files beside a Data folder — the Fallout 4 Script Extender (F4SE) 0.6.23 archive is what surfaced it — installing without the loader. Mosaic classified the archive as a BAIN complex package (its Data folder and its src source folder, which contains an f4se folder that is also a recognised data-folder name, both looked like sub-packages), and BAIN only installs the chosen sub-packages and silently discards loose files at the archive's root, so just the 58 Papyrus scripts were installed: no f4se_loader.exe and no f4se_1_10_163.dll. The only hint was a deploy-log line, "f4se_loader.exe not found — skipping launcher swap", and F4SE simply never started; installing the same archive through a collection did the same. An archive with a loose .exe or .dll at its root is now installed as an ordinary package. Checked against 1,159 real archives: this is the only classification that changes
- Fixed Mosaic launching tools with a different Proton than the one that built a game's prefix (for example GE-Proton instead of the system proton-cachyos-slr) when Steam records the prefix's tool as a sandbox-only /run/host path in its config_info file. Mosaic couldn't find that path on the host, gave up on identifying the game's Proton, and silently picked an arbitrary installed one instead. It now resolves the real location (or the same tool by name), and falls back to Steam's own default-tool setting last
- Fixed Windows tools that download things — installers, and any wizard that fetches a runtime inside Wine — reporting every download as failed when run against a Steam-created prefix. The wrapper Mosaic uses to re-create Steam's /run/host view replaces /run with an empty directory, and on systemd-resolved (and NetworkManager/resolvconf) systems /etc/resolv.conf is a link into /run, so inside the wrapper no name could be resolved (curl exit 6). It surfaced running MulderLoad's Fallout 4 downgrader, which deletes two game files (Fallout4 - TexturesPatch.ba2 and Fallout4IDs.ccc) before it downloads its patches, then found it couldn't fetch any of them and left the game folder missing those files. The wrapper now keeps the resolver's directory available; Steam's Verify Integrity restores anything already removed
- Fixed Fallout 4 loading only its official masters — none of the mods in the load order — on a Steam/Proton install. Mosaic deployed the load order to a lowercase plugins.txt, but the game reads (and creates on first launch) a capital-P Plugins.txt, and on Linux those are two different files: Wine handed the game its own two-line stub, so the deployed list was never read. Nothing failed visibly. The tell was in the script-extender plugins' own logs — every one that looks a form up by plugin name reported it "not found" (Rusty Face Fix: "Rusty Face Fix.esp|800 not found!", followed by a modal "FATAL ERROR" dialog that froze the game at its title screen; RobCo Patcher: dozens of "not found or is not a valid plugin file"). Fallout 4 now uses the engine's real Plugins.txt name, the same fix Skyrim Special Edition got in v1.0.12. An existing install picks it up on the next deploy; the old lowercase plugins.txt it left in the prefix is harmless and can be deleted. Fallout 4 VR still has the old lowercase default, since its real filename hasn't been confirmed
- Fixed "+ Add custom EXE…" (and "Add exe from game folder…") silently doing nothing — the Run dropdown just stayed on the default entry, with no message — when the game object had drifted out of sync with the selected profile after a background operation. Mosaic now re-syncs the active profile before saving the entry, and shows a warning if it still can't be saved instead of dropping it.

### Additions
- Added native game support for The Blood of Dawnwalker — a full built-in handler with its own routing rules (UE4SS Lua mods, .pak/LogicMods, engine .ini files routed into the Proton prefix, ReShade presets, and both the direct-DLL and proxy-DLL UE4SS loader install methods), matched against the same routing table the game's real Vortex extension ships
### Bug Fixes
- Fixed a UE4SS mod packaged with an extra wrapper folder above its actual per-mod folder (e.g. "Combat Camera - Configurable", shipped as Data/CombatCamera/Scripts/...) deploying one directory level too deep. Mosaic's UE5 deploy engine picked the very first folder in the mod's own internal archive layout as its per-mod destination folder, instead of the folder that actually held the mod's Scripts/dlls content, silently landing it somewhere the game's own Lua-based mod-menu framework never looks. This is a shared UE5 deploy-engine fix, so it also benefits any other UE5 game — built-in or custom — whose mods use this same wrapper-folder packaging shape

Every mod shipping one collided on the same destination path, so only one mod's copy ever actually reached disk, and Mosaic's own conflict UI reported whichever one deployed last as "overriding" every other, completely unrelated mod that also happened to ship this file
- Fixed The Blood of Dawnwalker and The Witcher Enhanced Edition showing a blank icon in the Add Game picker — a built-in game handler needs its own bundled icon file, unlike a custom game definition, which fetches one automatically, and neither had shipped with one. Also fixed the Add Game picker listing an already-configured game under "Not Installed" just because its install isn't tracked by Steam, Heroic, or Lutris (e.g. a manually-placed GOG copy) — a game that's already configured and working is now always treated as installed for this listing, regardless of how its files actually got there

- v1.2.1
### Bug Fixes
- Fixed a wizard tool (most visibly Script Merger for The Witcher 3, but any Proton-launched tool run against a game's own real Steam prefix could hit this) sometimes appearing to close itself seconds after opening — its window would still be sitting open and in active use on screen, but Mosaic had already decided the tool had exited and moved on. The practical effect could be severe: Mosaic restores the game's deployed mods back to vanilla as soon as it believes a wizard tool has closed, so this could silently wipe every deployed mod out from under a tool the user was still actively working in, with no action on their part. Mosaic now confirms the tool's actual window/process is gone before doing any cleanup, however long that takes

- v1.2.0
### Additions
- Added a "Sort Load Order (Dependencies)" wizard for Baldur's Gate 3 (Wizard ▸ Load Order and Config), looking at how BG3ModManager-Redux's own load-order advisor works: it computes the same dependency-correct order Mosaic already worked out internally for modsettings.lsx, but shows it first as a reviewable list of moves instead of the reorder only ever happening invisibly. Deploy itself now also runs this automatically — if the current load order doesn't satisfy a mod's declared meta.lsx dependencies, deploy corrects modlist.txt on its own and logs exactly what moved and why, instead of requiring a manual trip to the wizard every time a new dependency mod is installed
- Added a deploy-time warning, for every game, for any enabled mod with an un-ignored Nexus-declared missing requirement — the same yellow-exclamation flag already shown in the Mods tab, but previously only a passive icon that deploy ignored entirely even when a mod's required framework genuinely wasn't installed. The check cross-references currently-installed mods and the game's own native-framework detection (e.g. a Script Extender or Native Mod Loader Mosaic installs and verifies outside the normal mod list) before warning, so a requirement satisfied by another installed mod, or by a framework Mosaic tracks separately from staged mods, is never wrongly flagged. A missing requirement's own requirements are now also surfaced in the same pass, rather than one hop at a time — a chain like "this addon needs a framework mod, which itself needs a second framework" previously only revealed the second half after installing the first one and re-checking
- Added a "Languages" filter to the in-app Nexus browser, matching Nexus's own site search sidebar — narrow Browse, Trending, and Search results down to mods available in one or more specific languages
- Added a confirmation prompt when installing a Nexus file that shares its mod page with an already-installed mod but is a genuinely different file — e.g. a "Male" and "Female" variant of the same mod — instead of always silently merging it into the existing install with no way to tell afterward that a different file had been renamed into it. Replace the existing install, keep the new file as its own separate mod, or cancel
### Changes
- The footer's "Endorse" button (for Mosaic's own Nexus listing) is now a colored call-to-action instead of a flat button that looked identical to "Changelog"/"Github" and was easy to miss entirely, and keeps a green checkmark once endorsed instead of fading back into the background
### Bug Fixes
- Fixed a genuine circular dependency between two Baldur's Gate 3 mods (each declaring the other as a meta.lsx requirement) recursing forever during deploy and crashing it with a RecursionError, instead of being reported as the unresolvable conflict it actually is
- Fixed several places where the very first Nexus API call of a session — racing the app's own startup account check — could get rate-limited and silently treat a genuinely Premium account as non-Premium for that one action, falling back to a manual browser download a Premium account should never need: the in-app Nexus browser's Install button, the Missing Requirements panel's install action (which could also abort the install outright rather than just misroute it), Change Version, reinstalling a mod whose archive had gone missing, the shared hands-free wizard-download helper, and the curated-profile wizard. All now fall back to the last confirmed Premium status instead of assuming the account isn't Premium, matching a fix already applied to Collections and Quick Update

- v1.1.0
### Additions
- Added game support for The Witcher: Enhanced Edition. Loose-file mods deploy into a manager-created Data/override/ (never ships with the base game, and is removed if empty since the Aurora engine has been reported to crash on a present-but-empty override folder); System/-wrapped or loose ASI/ReShade proxy DLLs route to the game's real System/ folder; Documents/-wrapped save/config content routes into the Wine prefix's Documents/The Witcher/. Verified end-to-end — install, deploy, a live 54-mod Nexus Collection, restore — against both a real Steam install and a real GOG/Heroic install
- Added a "Fetch name from Nexus" button to both rename dialogs (the post-install prompt and the right-click "Rename mod" menu action), for mods installed from an archive downloaded manually rather than through Mosaic's own Nexus browser. The real mod-page title is already fetched and cached whenever such an archive gets matched to a Nexus mod at install time, but was previously only ever used for a per-file label in the auto-generated folder name — this surfaces it directly, on demand, instead of requiring a trip to the mod's Nexus page to copy-paste the name in by hand
### Changes
- Quick Update now also resolves an update for a mod whose author embeds the version number directly in each file's own Nexus label (e.g. "Modname 1.3" → "Modname 1.4") — every file gets a different label on each release for mods like this, so Mosaic's exact-name matching could never succeed on a version bump and silently deferred to manual Change Version every time, for any mod named this way. The looser match only trusts a result Nexus itself categorizes as the file's current Main or Update file, never a guess from the mod's archived version history
### Bug Fixes
- Fixed the built-in "UE5 (ue4ss)" custom game template silently failing to apply UE4SS's own DLL override for every game built from that preset, due to a typo in the template (`dwmpapi` instead of `dwmapi`). Also fixed a related issue where refreshing custom game templates from the shared repository could silently discard a locally-applied fix that hadn't been merged upstream yet — templates are now merged field by field instead of overwritten wholesale, so a local patch survives future syncs
- Fixed a mod's install position silently resetting to the top of the load order when a manual or drag-and-drop archive install replaced an existing mod whose on-disk folder name differed only in case from the newly-resolved name (e.g. a Nexus file-label casing drift between an author's uploads). The install pipeline's collision check only ever looked for an exact-case match, so it never recognized the existing folder as the same mod, silently installed a duplicate instead of updating it, and no user-visible confirmation ever fired to say so
- Fixed a mod that's already installed getting duplicated under a second folder, rather than updated in place, when a newer file for that same mod was downloaded directly from its Nexus page (e.g. a hotfix, via "Mod Manager Download") instead of through Mosaic's own update flow. Every Nexus file carries its own per-file display label distinct from the mod's title, so the hotfix's folder name never matched the existing install's name; a file Nexus itself categorizes Main or Update for a mod that's already installed now merges into the existing folder instead
- Fixed Quick Update failing every mod in a batch with "Premium required for direct download" for a genuinely premium account. The premium check made its own live account-status call immediately after the account API client had already made one of its own moments earlier while being built — Nexus rate-limits that call, and the second one could get rate-limited itself, with no distinction made between "your account isn't premium" and "the check itself failed to complete"
- Fixed a collection install's own end-of-run summary falsely reporting successfully-installed mods as failed, in the shape "N mod(s) did NOT install and are missing from the profile" immediately followed by each one's own status line reading "installed". The check looked for each mod's files in the wrong profile's folder, because the active profile had already been switched back to whatever it was before the install a few steps earlier in the same run
- Fixed a Proton prefix dependency (the VC++ Redistributable Mosaic installs automatically the first time a game's prefix is set up) never getting reinstalled if that prefix was later recreated — a fresh Steam Proton prefix, "Clear local Proton data", or a manually reset compatdata folder all leave a game's prefix carrying whichever old VC++ runtime Proton itself ships by default, silently, with nothing prompting a reinstall. The practical effect: a native tool that depends on the real runtime (a script extender, a native DLL/ASI injector) can fail or crash with no obvious link back to "the VC++ Redistributable is stale". This dependency check now reruns on every Deploy — the same always-verify, no-op-if-already-correct treatment Mosaic's Wine DLL overrides already got — rather than only once, when the game was first configured

- v1.0.14
### Bug Fixes
- Fixed "Change Version" (and a Collection install pinning an older file) failing to download a mod's archived or old-version files, with no way to get them except manually pressing "View" and downloading by hand. Nexus's direct download-link API can refuse to serve a file once it's no longer the current upload, even though the file's own page on the website still works — Mosaic now automatically falls back to opening that page and installing the file once the download completes, the same mechanism already used for non-premium accounts, except when the failure is a rate limit or an invalid API key, since a browser retry doesn't fix either of those
- Fixed a race that could require running Deploy twice after updating several mods close together. A Deploy queued behind one mod's update could be released before the next queued update had actually started installing, capturing the game's files with only the first update applied; a second Deploy, run once everything had settled, then picked up the rest. Deploy now correctly waits for the entire update queue to finish first

- v1.0.13
### Bug Fixes
- Fixed Mosaic's own "Install VC++ Redistributable" step — run automatically the first time a game's Proton prefix is set up, and available any time after via Proton Tools — silently failing on every real Steam-managed prefix, with nothing in the log beyond a bare exit code. A prefix that's only ever been touched by a real Steam launch has its Wine DLLs symlinked through a path that only exists inside Steam's own sandbox; Mosaic ran the installer directly, outside that sandbox, so it hit a dangling symlink and Wine couldn't even start. ### Bug Fixes
- Fixed Skyrim Special Edition (and, by the same inherited code path, Skyrim, Skyrim VR, and both Enderal editions) crashing within seconds of launching a large modlist, with every mod showing as loaded but disabled. Mosaic was deploying the game's plugin list as lowercase `plugins.txt`, but the Skyrim engine's own hardcoded filename is `Plugins.txt` — on Linux's case-sensitive filesystem these are two different files, so the copy Mosaic deployed was never the one the game actually read from or saved back to. The game's own periodic save created a separate, essentially empty file mid-session, and any mod that resolves one of its own plugins by name (Blade and Blunt, in the case that surfaced this) crashed the instant it tried. Mosaic now deploys under the game's real filename, and also re-checks Plugins.txt immediately before every launch and re-syncs it if it's drifted from what was deployed, in case anything else touches it mid-session
- Fixed a Collection with an "INI Tweaks" folder silently turning on per-profile INI file management the first time it was installed, even though nothing in Settings was ever touched. The practical effect: switching profiles could reset Skyrim.ini/SkyrimPrefs.ini to defaults, undoing in-game settings, because the feature's own bookkeeping had gaps — a newly linked profile with no ini files yet left the game with nothing, and turning the feature back off never restored a normal shared ini file. A Collection's ini tweaks now apply straight to the live ini when per-profile management isn't explicitly enabled, and enabling/disabling the feature in Settings now correctly seeds a new profile's copy and hands a normal file back on disable
- Fixed concurrent archive extraction during a collection install claiming all available CPU threads per archive regardless of how many extractions were running at once, which could push memory usage high enough to force other running applications to close. Threads are now divided by how many extractions are actually active at that moment rather than the configured ceiling, keeping the earlier fair-sharing fix without the extra slowdown of always assuming the ceiling is reached
- Fixed optional mods in a Collection's pre-install checklist defaulting to checked, which users mistook for required content and installed without meaning to. A collection with no prior install history now defaults every optional mod to unchecked; a collection you've already installed keeps remembering which options you kept or skipped, as before
- Fixed a collection's FOMOD mods installing as good as empty — only the files their installer always installs, none of the options — whenever the collection stored the author's choices in a different order than the mod's own installer steps presented them. Every one of the author's selections was silently discarded, with nothing in the log to say so. On one collection this reduced Skyrim Unbound Reborn from the 31 plugins the author selected to 1, and the two files it dropped were needed by 24 other mods, which then showed up as "missing master" errors on mods that had installed perfectly well themselves
- Fixed collections stopping to ask you to configure a FOMOD mod by hand even though the author had already recorded what they installed. A collection records an author's FOMOD setup in one of two ways — either the options they ticked, or the exact list of files those options produced — and Mosaic only ever read the first. Mods recorded the second way fell through to the installer wizard, leaving you to guess at options you have no way of knowing. Mosaic now reproduces the author's file list directly, matching each file by checksum so it works even where the installer renames files as it copies them. On a 2,400-mod collection this removed 27 wizard prompts, among them SMIM, Lux, Skyland AIO, Majestic Mountains and XP32 Maximum Skeleton — mods where a wrong guess quietly breaks a load order. If any file can't be matched with certainty the mod falls back to asking, rather than installing part of itself
- Fixed a collection installing a compatibility patch for a mod the collection doesn't actually include. A FOMOD can mark an option unusable when a mod it depends on is absent — an option you could never tick yourself in the wizard — but a choice recorded by the collection author was applied regardless. The patch's plugin then installed with a master file that was nowhere on disk. Such options are now skipped, and mods whose options depend on other mods wait until the rest of the collection is installed before deciding, so an option is never dismissed just because its dependency hadn't been installed yet
- Fixed a mod installing only part of itself when its archive contains both real game files at the top level and a folder further in that also looks like game data. Mosaic would decide the inner folder was the mod's real content and discard everything outside it. Requiem - Dragonborn Patch installed as a single 7 KB configuration file this way, dropping the plugin and archive that 25 other mods listed as a dependency. Mosaic now refuses to strip into a subfolder when doing so would throw away plugins, archives or game folders sitting at the top level
- Fixed a mod being downloaded again on every single collection install despite already sitting in the download cache, verified and intact. Nexus sometimes serves an archive whose name ends in .zip but which is really a RAR file; Mosaic checked such a file for damage as though it were a ZIP, concluded it was broken, deleted it as a failed download and fetched an identical copy — every run, indefinitely. Archive type is now judged by the file's actual contents rather than its name
