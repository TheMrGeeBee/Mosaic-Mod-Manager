## CI/CD
- Three workflows: `test-build.yml`, `build.yml`, `release.yml`
- Release pipeline triggers on `v*` tags
- Changelog extraction looks for `- v{major.minor.patch}` headers — keep that format exact
- **Dispatching `release.yml` manually (`workflow_dispatch`, e.g. `publish_nexus: true` from `main`) does NOT create a GitHub Release or publish the Flatpak GitHub Pages remote.** The `release` and `publish-pages` jobs are both gated on `github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')`, so a branch dispatch skips them — quietly (shows as `skipped` in `gh run view`, not a failure) rather than erroring, which makes it easy to miss. Hit this exact gap shipping v1.0.4: the Nexus upload went out fine via dispatch, but the app's own auto-updater (`Utils/version_check.py`, reads `GET /repos/.../releases/latest`) kept reporting the previous version since no tag or Release ever existed. Fix: push a real signed tag on the exact commit that was already built/tested — `git tag -s vX.Y.Z <commit> -m "Release X.Y.Z"` then `git push origin vX.Y.Z` (see `.claude/rules/signing-fix-instructions.md` for the signing convention). This is safe to do after an already-completed Nexus publish — it won't re-trigger `publish-nexus` (that job is dispatch-only gated, never satisfied by a plain tag `push` event), so no duplicate-upload risk.

## Wizard tool launches (Proton/wine) — lessons from the TW3 Script Merger debugging session (2026-09-15)

- **Wizard tools can report "closed" while genuinely still open.** `run_tool_logged`/`run_tool_winetricks_style` (`Utils/exe_launch/exe_launch.py`) track the Proton `runinprefix` launcher process via `proc.wait()` — but some .NET/WinForms GUI apps under wine (confirmed with WitcherScriptMerger's "Fresh & Automated Edition" build) detach from their inherited stdout pipe once their window is up, so `proc.wait()` returns within ~1-3s while the real tool is still running. Callers immediately follow with `wineserver -k` + `game.restore()` (undeploying every mod), which used to tear down a live user session mid-use with no user action at all. Fixed with `_wine_process_alive()`, which polls `/proc/*/cmdline` for the real exe's `argv[0]` suffix (not a full-cmdline substring match — that false-positives on any process merely mentioning the name, e.g. a shell command) with a ~20s grace period before concluding the tool actually exited quickly. This bug class likely affected every wizard tool run with "the game's own prefix" mode, not just Script Merger — if a similar "tool closed early / mods got wiped mid-session" report comes up for another tool, check here first.
- **The `/run/host` bwrap shim (`_apply_run_host_shim`) must be applied at every subprocess call site touching a real Steam prefix**, not just the main tool launch — a real Steam prefix (launched normally through SteamLinuxRuntime at least once) has its `system32` DLLs symlinked through `/run/host/...`, which only resolves inside that sandbox. `install_dotnet_runtime` (`Utils/wine_proton/proton_tools.py`) and `shutdown_prefix_wineserver` (`exe_launch.py`) were both silently missing it — the first failed installs with exit 53 / "could not load kernel32.dll", the second's `wineserver -k` just silently no-op'd. Also double check the *path* passed to the shim check: `run_tool_logged` was passing `STEAM_COMPAT_DATA_PATH` (the compat-data root) instead of `.../pfx` (the actual prefix dir containing `drive_c`), so `_needs_run_host_shim`'s `kernel32.dll` readlink check always missed and the shim silently never applied.
- **WitcherScriptMerger reads `MergeInventory.xml` and its `GameDirectory` config setting from wherever its own exe lives** (Mosaic's `Applications/ScriptMerger/`, written by `update_witcher3_script_merger_config` in `Utils/exe_launch/exe_args_builder.py`) — never the actual Steam game folder. A `<Game>/Witcher Script Merger` folder, which some Nexus mod authors' manual-install instructions describe, is not needed or read by Mosaic's setup.
- **Never seed `Applications/ScriptMerger/MergeInventory.xml` from a Nexus collection author's own "ready to play" download.** It encodes *their* enabled-mod-set (e.g. including their own pre-baked "Merged Scripts"/`mod0000_MergedFiles` as a legitimate merge source), and the per-profile snapshot mechanism (`Utils/modding_tools/script_merger_inventory.py`'s `snapshot_inventory`/`restore_inventory`) faithfully carries that contamination forward into every future run, so WSM keeps building new merges on top of a source that may be disabled in the user's own setup. `purge_merges()` (same module) resets it cleanly if this happens.
- **A collection's pre-baked "ready to play" merge (e.g. `mod0000_MergedFiles`/"Merged Scripts") must never be enabled at the same time as the individual mods it covers**, whether that's the author's own sources or your own fresh Script Merger run against them — causes real WitcherScript "Function X is already defined in class Y" compile errors at game launch, not a Mosaic bug. Pick one: the author's premade merge (its source mods disabled) or your own Script Merger run (the premade merge disabled).
- `WitcherScriptMerger.dll.config`'s `CheckBundles=0` (Mosaic's shipped default) means bundle-level conflicts are never checked, only Scripts/XML — a collection's separately-downloadable "Bundle Content"/"Merge Inventory File" Nexus files are for the fully-manual, don't-run-the-tool-at-all install path, not something a live WSM run ever consumes.
- **Testing a fix against a running instance:** if Mosaic is running from the packaged AppImage, editing the source tree has zero effect on it — the AppImage bundles its own separate copy of the Python source. Close the AppImage instance and run `./run_qt.sh` from `src/` to pick up source changes immediately. Also, an already-running *source* instance needs restarting too after any further edit (Python doesn't hot-reload).
