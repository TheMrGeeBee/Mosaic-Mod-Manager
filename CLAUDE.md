## CI/CD
- Three workflows: `test-build.yml`, `build.yml`, `release.yml`
- Release pipeline triggers on `v*` tags
- Changelog extraction looks for `- v{major.minor.patch}` headers — keep that format exact
- **Dispatching `release.yml` manually (`workflow_dispatch`, e.g. `publish_nexus: true` from `main`) does NOT create a GitHub Release or publish the Flatpak GitHub Pages remote.** The `release` and `publish-pages` jobs are both gated on `github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v')`, so a branch dispatch skips them — quietly (shows as `skipped` in `gh run view`, not a failure) rather than erroring, which makes it easy to miss. Hit this exact gap shipping v1.0.4: the Nexus upload went out fine via dispatch, but the app's own auto-updater (`Utils/version_check.py`, reads `GET /repos/.../releases/latest`) kept reporting the previous version since no tag or Release ever existed. Fix: push a real signed tag on the exact commit that was already built/tested — `git tag -s vX.Y.Z <commit> -m "Release X.Y.Z"` then `git push origin vX.Y.Z` (see `.claude/rules/signing-fix-instructions.md` for the signing convention). This is safe to do after an already-completed Nexus publish — it won't re-trigger `publish-nexus` (that job is dispatch-only gated, never satisfied by a plain tag `push` event), so no duplicate-upload risk.

## Wizard tool launches (Proton/wine) — lessons from the TW3 Script Merger debugging session (2026-09-15)

- **Wizard tools can report "closed" while genuinely still open.** `run_tool_logged`/`run_tool_winetricks_style` (`Utils/exe_launch/exe_launch.py`) track the Proton `runinprefix` launcher process via `proc.wait()` — but some .NET/WinForms GUI apps under wine (confirmed with WitcherScriptMerger's "Fresh & Automated Edition" build) detach from their inherited stdout pipe once their window is up, so `proc.wait()` returns within ~1-3s while the real tool is still running. Callers immediately follow with `wineserver -k` + `game.restore()` (undeploying every mod), which used to tear down a live user session mid-use with no user action at all. Fixed with `_wine_process_alive()`, which polls `/proc/*/cmdline` for the real exe's `argv[0]` suffix (not a full-cmdline substring match — that false-positives on any process merely mentioning the name, e.g. a shell command) with a ~20s grace period before concluding the tool actually exited quickly. This bug class likely affected every wizard tool run with "the game's own prefix" mode, not just Script Merger — if a similar "tool closed early / mods got wiped mid-session" report comes up for another tool, check here first.
- **The `/run/host` bwrap shim is now applied centrally inside `proton_run_command` (`Utils/wine_proton/steam_finder.py`, helpers in `Utils/wine_proton/run_host_shim.py`)** — any argv built through it whose `env["STEAM_COMPAT_DATA_PATH"]/pfx` needs it gets wrapped, so a new launch path can't forget it (Run EXE was the fifth site to hit this, 2026-09-19). `_apply_run_host_shim` is idempotent, so the older per-site calls are harmless no-ops. The flatpak and plain-`wine`-binary branches are left alone, and **anything that does NOT go through `proton_run_command`** (a raw `wine`/`wineserver -k`/`reg` invocation) still needs `_apply_run_host_shim` explicitly. The original rule, kept for that case: it must be applied at every subprocess call site touching a real Steam prefix, not just the main tool launch — a real Steam prefix (launched normally through SteamLinuxRuntime at least once) has its `system32` DLLs symlinked through `/run/host/...`, which only resolves inside that sandbox. `install_dotnet_runtime` (`Utils/wine_proton/proton_tools.py`) and `shutdown_prefix_wineserver` (`exe_launch.py`) were both silently missing it — the first failed installs with exit 53 / "could not load kernel32.dll", the second's `wineserver -k` just silently no-op'd. Also double check the *path* passed to the shim check: `run_tool_logged` was passing `STEAM_COMPAT_DATA_PATH` (the compat-data root) instead of `.../pfx` (the actual prefix dir containing `drive_c`), so `_needs_run_host_shim`'s `kernel32.dll` readlink check always missed and the shim silently never applied.
- **WitcherScriptMerger reads `MergeInventory.xml` and its `GameDirectory` config setting from wherever its own exe lives** (Mosaic's `Applications/ScriptMerger/`, written by `update_witcher3_script_merger_config` in `Utils/exe_launch/exe_args_builder.py`) — never the actual Steam game folder. A `<Game>/Witcher Script Merger` folder, which some Nexus mod authors' manual-install instructions describe, is not needed or read by Mosaic's setup.
- **Never seed `Applications/ScriptMerger/MergeInventory.xml` from a Nexus collection author's own "ready to play" download.** It encodes *their* enabled-mod-set (e.g. including their own pre-baked "Merged Scripts"/`mod0000_MergedFiles` as a legitimate merge source), and the per-profile snapshot mechanism (`Utils/modding_tools/script_merger_inventory.py`'s `snapshot_inventory`/`restore_inventory`) faithfully carries that contamination forward into every future run, so WSM keeps building new merges on top of a source that may be disabled in the user's own setup. `purge_merges()` (same module) resets it cleanly if this happens.
- **A collection's pre-baked "ready to play" merge (e.g. `mod0000_MergedFiles`/"Merged Scripts") must never be enabled at the same time as the individual mods it covers**, whether that's the author's own sources or your own fresh Script Merger run against them — causes real WitcherScript "Function X is already defined in class Y" compile errors at game launch, not a Mosaic bug. Pick one: the author's premade merge (its source mods disabled) or your own Script Merger run (the premade merge disabled).
- `WitcherScriptMerger.dll.config`'s `CheckBundles=0` (Mosaic's shipped default) means bundle-level conflicts are never checked, only Scripts/XML — a collection's separately-downloadable "Bundle Content"/"Merge Inventory File" Nexus files are for the fully-manual, don't-run-the-tool-at-all install path, not something a live WSM run ever consumes.
- **Testing a fix against a running instance:** if Mosaic is running from the packaged AppImage, editing the source tree has zero effect on it — the AppImage bundles its own separate copy of the Python source. Close the AppImage instance and run `./run_qt.sh` from `src/` to pick up source changes immediately. Also, an already-running *source* instance needs restarting too after any further edit (Python doesn't hot-reload).

## Fallout 4 Old-Gen collections and the Downgrade wizard (2026-09-19)

- **Steam serves the Anniversary Edition (1.11.240); Old-Gen collections ("A StoryWealth" etc.) need 1.10.163 + F4SE 0.6.23** (`f4se_1_10_163.dll`). Running them on 1.11.240 doesn't crash — F4SE just silently refuses most plugins. Tell-tale: `<prefix>/Documents/My Games/Fallout4/F4SE/f4se.log` full of "no version data" / "disabled, incompatible" (6 of 63 loaded on "A StoryWealth").
- **The downgrade only patches three root files** (`Fallout4.exe`, `Fallout4Launcher.exe`, `steam_api64.dll`) — `Data/` stays Anniversary, and `BackportedBA2Support.dll` (shipped by the collection) lets the Old-Gen exe read it. So, unlike Skyrim's downgrader, `Data_Core/` isn't in the way. The wizard is `wizards_qt/fallout4_downgrade_view.py` over the pure core `Utils/modding_tools/fo4_downgrade.py` (backup → xdelta3 to temp → verify version via `Utils/wizard_support/pe_version.py` → swap; rolls back on any failure; revert from the hash-checked backup). Patch source: Nexus mod 98059, file 407852 — a flat zip of `Fallout4exe.xdelta`, `Fallout4Launcherexe.xdelta`, `SteamAPI64.xdelta` (**dot dropped from `.exe`, underscore dropped from `steam_api64`** — the first `find_patches` guessed conventional names and failed on the real archive; it now compares names with punctuation squashed, longest match wins). Verified 2026-09-19: the real patches apply through real xdelta3 to a real 1.11.240 install → `Fallout4.exe` 1.10.163.0 / launcher 1.3.22.0 / `steam_api64.dll` 2.89.45.4, and revert byte-for-byte.
- **Mosaic is the NXM handler.** Nexus's "Mod Manager Download" on the patch page makes Mosaic fetch it into `download_cache/<game>/` **and install it as a mod** (3 loose `.xdelta` files land in the profile — remove that mod). The wizard's download step tells users to use Manual download, reuses an archive already in the cache (matched exactly by its `.fileid` sidecar via `_find_cached_archive`), and its Locate step also scans `list_all_cache_dirs()`. `NexusDownloader.download_file` (the premium hands-free fetch) only looks in the Downloads dir, not the per-game cache, so without that check it would re-download a file already on disk.
- **FIXED 2026-09-19: the F4SE 0.6.23 archive used to install without its loader.** It is `f4se_0_06_23/{Data/, src/, f4se_loader.exe, f4se_1_10_163.dll, f4se_steam_loader.dll, ...}`; `detect_bain` saw `Data` + `src` as two sub-packages (`src/f4se` is a recognised data-dir name — an accident of naming; SKSE64's `src/skse64` isn't), remembered the selection `["Data"]`, and BAIN drops loose root files, so only the 58 scripts were staged and deploy logged `f4se_loader.exe not found — skipping launcher swap`; F4SE never started. `detect_bain` now treats a loose `.exe`/`.dll` at the archive root (`_ROOT_PAYLOAD_EXTS`) as "simple package". **A broader "a top-level `Data/` means simple" rule was tried on paper and rejected** after a dry run over 1,159 cached archives: it would have flipped 6, including genuine alternates that must stay a picker (Red Shift PA's `DATA` + `Optional esl version`, Photo Mode's `Data` + `Photos`). The narrow rule changes exactly one archive (F4SE). A reinstalled F4SE also stages its 344 source files under `src/` (deployed to `Data/src/`, harmless — `src` is a valid top-level folder for Bethesda mods).
- **The collection's own FO4Down.exe is unusable under Proton**: Terminal.Gui TUI, .NET ICU crash (exit 82), interactive Steam login, and it predates 1.11.x. Don't try to make Run EXE drive it.
- **Downgrade only while undeployed**: deploy swaps `Fallout4Launcher.exe` for the F4SE loader and parks Steam's real one in `Fallout4Launcher.bak` (`script_extender_swap`). The wizard refuses while `.bak` exists and offers Restore via `ctx.run_restore` (the app's real `_on_restore`; `game.restore()` alone skips root-flagged mods and the deploy flag).
- **The F4SE wizard installs the *latest* F4SE and overwrote the collection's pinned 0.6.23 in place** (same Nexus mod id). After downgrading, reinstall the collection's file (still in `download_cache/Fallout 4/Fallout 4 Script Extender (F4SE)-42147-0-6-23-*.7z`). An F4SE version selector for the wizard was deliberately not built (Nexus archive naming changed over time; the keyword match is AND-only).
- **A Steam update of Fallout 4 re-downloads the three exes** — rerun the wizard. Mosaic never edits Steam's `appmanifest`.
- `find_proton_for_game` order: per-game mapping → `compatdata/<id>/config_info` (may hold sandbox-only `/run/host/...` paths, now stripped) → Steam's default tool (key `"0"`). Before the fix it returned None for `proton-cachyos-slr` prefixes and Run EXE fell back to an arbitrary Proton.
- The Flatpak manifest has no xdelta3 module (untested change would risk the release build) — Flatpak users see the wizard's install hint.
